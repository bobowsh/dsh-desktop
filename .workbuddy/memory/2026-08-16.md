## release.yml 在 CI 打不出 .dsh/profiles/web 插件与 .mnemon/bin 的根因与修复
- 根因三层：(1) `.gitignore` 整目录忽略 `bundled-user-data/`，web profile 的 manifest 全没进版本库；(2) `scripts/bundle-user-data.mjs` 从构建机 home(`~/.dsh`/`~/.mnemon`)拷贝，GitHub runner 上这两样都不存在 → skip → 打空包；(3) `npm ci` 只装桌面壳自身依赖，web profile 那套 pnpm 插件 + mnemon.exe 从没在 CI 装过。
- 插件机制：`dsh plugin --profile web add xxx` 本质是薄转发层——`resolveProfileDir` 走 `resolveDshHome()`(吃 `DSH_HOME` 环境变量)，把参数原样 `spawnSync("pnpm", args)` 在 profile 目录跑，再 reconcile `dsh.profile.bundles`。`initProfile` 只写 `cordis.yml`(PROFILE_ROOT_FILENAME)，**不会碰 package.json**，所以 CI 用 `dsh plugin --profile web install --frozen-lockfile` 安全(用提交的 lockfile 复现，不重新解析版本)。
- pnpm v11 deny-by-default 坑：web profile 里 12+ 个 `github:` 插件安装跑 `prepare` 构建脚本、传递依赖 `node-pty` 有 install/postinstall。CI 非交互模式(无 TTY、无 `CI=true`)会被 deny。锁文件里无 `onlyBuiltDependencies` 字段，故必须在 `bundled-user-data/.dsh/profiles/web/pnpm-workspace.yaml` 加 `allowBuilds`(列 15 个 github 包名 + node-pty)——已本地全新 `pnpm install --frozen-lockfile`(无 CI=true)验证 EXIT=0、无 deny。
- mnemon.exe 来源：`github.com/mnemon-dev/mnemon` 的 Go 二进制，README 写 `go install`；但 GitHub Releases 有 Windows 包 `mnemon_0.2.3_windows_amd64.zip`(最新 v0.2.3)。CI 直接下载解压即可，无需装 Go。
- 改动清单：① `.gitignore` 去掉 blanket `bundled-user-data/`，改为只忽略 `bundled-user-data/.mnemon/`(node_modules 已被全局规则忽略)；② `pnpm-workspace.yaml` 加 `allowBuilds`；③ 提交默认 `bundled-user-data/.dsh/settings.yaml`(去掉 llm-pi-ai/agent-default-model 等个人模型配置、cliPath 置 `@@MNEMON_CLI@@` 占位符，与 bundle-user-data.mjs 的 strip 逻辑一致，安装时 NSIS 改写成本机路径)；④ `release.yml` 的 windows-x64 job：加 `pnpm/action-setup@v4`(v11)，打包前插入 pwsh staging 步骤(`npm -g install @deepseek-ai/dsh@0.1.0-rc.6` → 设 `DSH_HOME=bundled-user-data/.dsh` → `dsh plugin --profile web install --frozen-lockfile` → 下载 mnemon.exe 到 `.mnemon/bin`)。`package:win` 内的 bundle-user-data.mjs 因 home 为空会 skip，in-place 填好的 bundled-user-data 原样被 extraResources 打包。

## 执行命令弹黑窗口的根因（dsh-desktop-me + deepseek-harness）
- 桌面壳本身没问题：`src/main/runtime/harness-runtime.ts` 的 `buildHarnessSpawnOptions` 启动 harness 子进程时已设 `windowsHide: true`（第 64 行），不会弹窗。
- 真正弹窗发生在 harness 内部执行命令：
  `dsh-bash-local` → `ctx.subprocess.spawn(spec)` → `@deepseek-ai/dsh-subprocess-local` 的 `spawnSubprocess()`（`node_modules/@deepseek-ai/dsh-subprocess-local/lib/index.js:548`）调用 Node `spawn(program, args, { cwd, env, stdio, detached })` **漏了 `windowsHide: true`**。
- Windows 上 Node 默认 `windowsHide: false` → 每次执行命令都会分配一个可见控制台（黑）窗口。
- 同仓 `dsh-host-directory-picker-native`、`dsh-native-command` 都显式写了 `windowsHide: true`，说明 `dsh-subprocess-local` 这一处是被遗漏的 bug（不是有意为之）。
- 修复：给 `spawnSubprocess` 的 spawn options 加 `windowsHide: true`；用 patch-package 固化成 `patches/@deepseek-ai+dsh-subprocess-local+0.1.0-rc.6.patch`（package.json 的 postinstall 已自动跑 `patch-package`）。一处修复同时覆盖 Bash 与 Shell 两种命令执行（都走 dsh-subprocess-local）。

## 为什么 deepseek-harness-desktop（"另一家"）没给 dsh-subprocess-local 打补丁
- 它不是"漏修"，而是**依赖树里根本没有 `@deepseek-ai/dsh-subprocess-local`**：查过它的 `.yarn/cache/*.zip` 与磁盘 `node_modules`，均无此包。它用 Yarn 4 (PnP)，根 package.json 是 workspace，真正的桌面壳在 `dsh-plugin-desktop` 子包；该子包只列了 `dsh-subprocess`（接口）和 `dsh-bash-local`，未列 `dsh-subprocess-local`。
- 对照 dsh-desktop-me：`dsh-subprocess-local` 是**直接依赖**，命令执行 100% 走它 → 弹窗必现，必须 patch。
- "另一家"只 patch 了它确实用到且 Win32 特定的 `dsh-sandbox-windows-acl`（`wShowWindow:0`），因为 sandbox 走 Win32 `CreateProcessAsUserW`，窗口问题必现。
- 结论：两个项目补丁范围不同，**根因是命令执行后端依赖不同**，不是谁修漏了。dsh-desktop-me 当前的补丁（subprocess-local + sandbox-windows-acl）是正确且必要的。
